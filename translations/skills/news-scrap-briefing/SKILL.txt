# 뉴스 스크랩 브리핑

## 이 스킬이 하는 일

사용자가 지정한 기사들 — 직접 URL, 사이트+주제/키워드, 또는 "방금 대화에서 봤던 그 기사들" —
을 대상으로 이 스킬은 다음을 수행합니다:

1. **Playwright MCP**(`mcp__playwright__*` 도구)로 각 기사를 스크랩하고, 시각적 증거로
   각 기사의 전체 화면 스크린샷을 캡처합니다.
2. 스크랩한 내용(헤드라인, 출처, 본문)을 분석해 기사별 짧은 요약과 핵심 포인트 몇 가지,
   그리고 전체 기사를 아우르는 종합 정리를 만듭니다.
3. 이 분석 결과를 **하나의 공유 JSON 파일**로부터 두 번 렌더링합니다:
   - `scripts/build_docx_report.py`(`python-docx`)로 만드는 워드 보고서
   - `scripts/build_pptx_deck.py`(`python-pptx`)로 만드는 파워포인트 덱

두 생성기 모두 형제 스킬인 `research-report-docx`의 `build_report.py`처럼
데이터 기반(data-driven) 방식입니다. 내용을 요약한 JSON을 넘기면 일관된
스타일링(맑은 고딕, 크기가 지정된 제목, 지정 가능한 메인 컬러)을 알아서
처리해주므로, 워드/파워포인트 서식이 아니라 스크랩과 분석 자체에 집중할 수
있습니다.

## 작업 순서

### 1. 필요 시 범위 확인

스크랩 전에 대상 기사 범위를 정합니다:

- **직접 URL** — 해당 URL들만 그대로 스크랩합니다.
- **사이트 + 주제/키워드** (예: "네이버 뉴스 IT/과학 탭에서 AI 관련 기사") —
  목록 페이지로 이동해 주제에 맞는 기사를 찾고, 적절한 개수를 선택합니다.
- **이 대화에서 이미 열어보거나 찾은 기사를 가리키는 경우** — 다시 검색하지
  않고 그 기사들을 재사용합니다.

사용자가 개수를 지정하지 않았다면 기본값은 **3~5개 기사**로 합니다 — 간단한
브리핑이 과도한 리서치 프로젝트로 번지지 않으면서도 실제 비교/종합이 가능한
분량입니다. 요청이 정말로 모호하다면(URL도, 사이트도, 주제도 전혀 없는 경우)
스크랩 전에 짧게 확인 질문을 합니다. URL이나 명확한 주제+사이트가 이미
주어졌다면 과도하게 되묻지 않습니다.

### 2. Playwright MCP로 각 기사 스크랩

각 기사마다 다음을 수행합니다:

1. `mcp__playwright__browser_navigate`로 기사 URL로 이동합니다.
2. `mcp__playwright__browser_snapshot`(또는 `browser_find`)로 헤드라인,
   기자/출처, 본문을 읽어 분석에 사용하고, 기사 본문 컨테이너(헤드라인+
   본문을 감싸는 요소 — `<body>` 전체가 아님)의 `ref`를 확보합니다.
3. `mcp__playwright__browser_take_screenshot`을 `fullPage: true`가 아니라
   **해당 본문 요소로 스코프**해서(그 요소의 ref를 `target`/`element`로
   전달) 실행합니다. 실제 기사 페이지는 스크롤 아래로 관련기사 영역,
   댓글 섹션, 푸터가 이어지는데, 이걸 전부 포함한 말 그대로의 전체 페이지
   캡처는 극단적으로 세로가 길고 얇은 이미지(일부 뉴스 사이트는
   5,000~10,000px 이상)가 되어 삽입했을 때 보기 좋지 않고, 기사 자체보다
   증거로서 더 나을 것도 없습니다. 단일 본문 요소를 확신 있게 식별할 수
   없다면 `fullPage: true`로 대체하되, 훨씬 더 긴 이미지가 나올 것을
   감안하세요 — 생성기가 문서 내 렌더링 크기는 제한해주지만, 1:10 같은
   가로세로 비율 자체를 보기 좋게 만들어주지는 못합니다.

모든 스크린샷은 이 프로젝트의 Playwright 출력 규칙에 따라 `output/playwright/`
아래, 이번 브리핑을 위한 하위 폴더에 저장합니다. 예:
`output/playwright/news-scrap-briefing/<주제-또는-날짜>/article-1.png`,
`article-2.png` 등 — 기사 1개당 스크린샷 1장, 발표 순서대로 번호를 매깁니다.

목록 페이지를 거치는 경우(사이트+주제 모드), 먼저 목록/검색 페이지에
도달하게 되는데 — 전체 화면 스크린샷이 필요한 것은 개별 기사 페이지뿐이며,
목록 페이지 자체는 필요하지 않습니다.

### 3. 조사 결과를 하나의 공유 JSON 파일로 구조화

아래 스키마에 맞춰 JSON 파일(예: 임시/스크래치 위치에)을 작성합니다 —
이 파일이 **두 생성기 모두**를 구동합니다:

```json
{
  "title": "브리핑 주제 또는 헤드라인 테마",
  "subtitle": "한 줄 범위 설명, 예: 날짜나 사이트명",
  "color": "#1F4E79",
  "sections": [
    {
      "heading": "Overview",
      "paragraphs": ["스크랩한 모든 기사를 아우르는 1~3문장 종합 — 공통 주제, 눈에 띄는 이견, 또는 트렌드."]
    },
    {
      "heading": "기사 헤드라인 원문 그대로",
      "source": "매체명 · https://article-url",
      "paragraphs": ["이 기사의 1~2문장 요약."],
      "bullets": ["핵심 포인트 1", "핵심 포인트 2"],
      "image": "output/playwright/news-scrap-briefing/<주제>/article-1.png"
    },
    {
      "heading": "Key Takeaways",
      "bullets": ["종합 포인트 1", "종합 포인트 2"],
      "include_in": ["pptx"]
    },
    {
      "heading": "Sources",
      "bullets": ["기사 헤드라인 — https://article-url", "..."],
      "include_in": ["docx"]
    }
  ]
}
```

가이드라인:

- 기사 1개당 섹션 1개(heading = 기사의 실제 헤드라인, source = 매체명+URL,
  image = 2단계에서 저장한 해당 기사의 스크린샷 경로)로 구성합니다. Overview
  섹션을 가장 먼저, 그다음 발표 순서대로 기사별 섹션을, 마무리 섹션은 마지막에
  둡니다.
- `include_in: ["pptx"]` / `["docx"]`는 특정 섹션을 한쪽 산출물에만
  포함시킵니다 — 보고서의 Overview와 중복될 "Key Takeaways" 종합 슬라이드나,
  슬라이드보다 문서 부록에 더 어울리는 원본 URL "Sources" 목록에 사용하세요.
  Overview와 기사별 섹션처럼 양쪽 모두에 들어가야 하는 섹션은 `include_in`을
  아예 생략합니다.
- 사용자가 특정 메인 컬러를 요청했다면 그 값을 `"color"`에 hex 코드로
  넣습니다. 그렇지 않으면 생성기가 기본 네이비 색상을 사용합니다.
- bullets는 실제로 짧게 유지합니다(문서 불릿일 뿐 아니라 슬라이드 불릿으로도
  렌더링되므로) — 문단이 아니라 짧은 구절이나 한 문장 정도로 씁니다.

### 4. 두 문서 생성

```bash
python "<skill-dir>/scripts/build_docx_report.py" --input briefing.json --output "<주제> briefing.docx"
python "<skill-dir>/scripts/build_pptx_deck.py" --input briefing.json --output "<주제> briefing.pptx"
```

생성 시점에 사용자가 색상을 지정하면 두 명령 모두에 `--color "#RRGGBB"`를
전달해 JSON의 `"color"` 필드를 덮어쓸 수 있습니다. 전체 스키마 참고는 각
스크립트의 모듈 docstring을 확인하세요.

### 5. 두 파일 모두 전달

두 산출물을 사용자의 다른 생성 문서가 저장되는 위치에 저장하고(불명확하면
질문), 사용자에게 전달합니다. 무엇을 스크랩했는지, 각 기사의 핵심 포인트가
무엇이었는지, 그리고(있다면) 어떤 섹션이 보고서 또는 덱 중 한쪽에만
들어갔는지를 간단히 요약해 사용자가 신뢰하기 전에 내용을 검증할 수 있게
합니다.

## 왜 이런 구조인가

하나의 JSON, 두 개의 렌더러: 보고서와 덱은 별개의 두 원고가 아니라 같은
분석을 보는 두 개의 시각이므로, (`include_in`만을 유일한 예외 통로로 두고)
스키마를 호환되게 유지하면 두 산출물의 내용이 자동으로 동기화됩니다 —
JSON을 한 번만 수정해 요약을 고치면, 다음 생성 실행에서 두 산출물 모두
그 변경을 반영합니다.

## 참고 사항

- `python-docx` 또는 `python-pptx`가 설치되어 있지 않다면 먼저 설치합니다
  (`pip install python-docx python-pptx`).
- 현재 환경에서 Playwright MCP 도구를 사용할 수 없다면, 다른 스크래핑
  방법으로 조용히 대체하지 말고 그 사실을 명시적으로 알립니다 — 사용자가
  구체적으로 Playwright를 요청했기 때문입니다.
- 특정 기사 페이지가 전체 화면 스크린샷을 막는 경우(페이월, 무거운 지연
  로딩 등), 가능한 최선의 스크린샷을 찍고 해당 기사 요약에 그 한계를
  기록합니다 — 내용을 지어내지 않습니다.
- URL 1개만 요청받은 경우에도 동일한 스키마를 사용합니다 — Overview와
  마무리 섹션 사이에 기사 섹션이 1개만 있는 형태가 됩니다.
- 두 생성기 모두 스크린샷을 삽입하기 전에 자동으로 축소·재압축합니다
  (`scripts/image_utils.py` 사용) — 전체 화면 스크린샷은 세로 길이가 수천
  픽셀에 용량이 수 메가바이트에 달할 수 있기 때문입니다. JSON의 `"image"`
  필드에 스크린샷을 지정하기 전에 직접 리사이즈할 필요는 없습니다.
