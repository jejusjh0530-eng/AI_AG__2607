# gws-calendar

## 이 스킬이 하는 일

이 프로젝트에 이미 인증되어 있는 `gws` CLI(Google Workspace CLI)를 사용해 사용자의 실제 Google 캘린더에 일정을 예약하고, 일정을 바꾸고, 취소합니다 — 제안이나 초안이 아니라 캘린더에 대한 실제 쓰기 작업입니다. 읽기와 브리핑만 하는 `일정관리` 서브에이전트의 반대편에 있는 스킬입니다. 사용자가 자신의 일정을 확인하고 싶어할 뿐이라면 이 스킬이 아니라 그쪽을 사용해야 합니다.

## 시작하기 전: gws 인증 확인

```bash
npx --yes @googleworkspace/cli auth status
```

`"scopes"`에 `https://www.googleapis.com/auth/calendar`가 있는지 확인하세요. 없다면 아래 호출들이 (도움이 되는 메시지 없이) 인증 오류(exit code 2)로 실패하므로, 미리 확인하는 편이 좋습니다. 이 프로젝트에서 다른 서비스용으로 이미 승인받은 스코프를 잃지 않으면서 스코프를 추가하려면:

```bash
npx --yes @googleworkspace/cli auth login --services calendar,docs,drive,gmail,forms
```

이 명령은 브라우저 동의 URL을 엽니다 — 현재 세션에서 브라우저 자동화 도구를 사용할 수 있다면 직접 진행하고, 그렇지 않다면 URL을 사용자에게 공유해 완료해 달라고 요청하세요.

## 날짜 계산 전에 "오늘"을 먼저 고정하기

"다음주 금요일", "내일 오후 3시", "이번 주말" 같은 요청은 실제 현재 날짜를 기준으로 해야만 의미가 있습니다 — 맥락에서 추측하지 마세요. 실제 값을 가져오세요.

```bash
date "+%Y-%m-%d %A"
```

사용자의 맥락이 명확히 다른 것을 가리키지 않는 한 기본 시간대는 `Asia/Seoul`(`+09:00`)로 합니다.

## 일정 등록

1. **구체적인 필드 추출.** 사용자의 요청에서 제목(`summary`), 시작 시간, 종료 시간(또는 소요 시간), 장소, 설명, 참석자 이메일, 반복 여부를 뽑아냅니다. 소요 시간은 줬지만 종료 시간이 없으면 계산하고, 둘 다 없으면 시간이 있는 일정 기준으로 기본값 **1시간**을 사용하되, 사용자가 요청하지 않은 값을 조용히 골라놓고 아무 말도 안 하는 대신 확인 메시지에서 이 가정을 밝히세요.

2. **일정 본문 구성.** 시간이 있는 일정의 경우:

   ```json
   {
     "summary": "팀 회의",
     "location": "회의실 A",
     "description": "분기 리뷰",
     "start": {"dateTime": "2026-08-28T15:00:00+09:00", "timeZone": "Asia/Seoul"},
     "end":   {"dateTime": "2026-08-28T16:00:00+09:00", "timeZone": "Asia/Seoul"},
     "attendees": [{"email": "someone@example.com"}],
     "recurrence": ["RRULE:FREQ=WEEKLY;COUNT=4"]
   }
   ```

   종일 일정은 `start`와 `end` 양쪽 모두 `dateTime`/`timeZone` 대신 `{"date": "2026-08-28"}`를 사용하세요 — Calendar API는 종일 일정의 `end.date`를 배타적(exclusive)으로 취급한다는 점(일정이 포함하는 마지막 날의 *다음 날*)을 기억하세요. 여러 날짜에 걸친 종일 일정을 만들 때 이를 잊으면 흔히 실수하게 됩니다.

3. **등록:**

   ```bash
   gws calendar events insert --params '{"calendarId":"primary","sendUpdates":"none"}' --json '<2단계의 본문>'
   ```

   `sendUpdates`는 기본값 `"none"`으로 두어 참석자에게 자동으로 메일이 가지 않게 합니다. 사용자가 명시적으로 알림/초대를 요청했을 때만 `"all"`로 바꾸세요 — 사용자의 Google 계정을 통해 다른 사람에게 메일을 보내는 것은 조용한 기본값이 아니라 미리 알려야 할 부작용입니다.

4. **평이한 말로 확인.** 원시 RFC3339 문자열이 아니라 사용자가 쓴 표현("금요일 오후 3시")으로 확인해주고, 응답의 `htmlLink`를 함께 안내해 사용자가 직접 열어서 다시 확인할 수 있게 하세요.

## 일정 수정

애매한 언급만으로 어떤 일정을 건드릴지 절대 추측하지 마세요 — 먼저 찾아보세요.

1. **찾기:**

   ```bash
   gws calendar events list --params '{"calendarId":"primary","timeMin":"<범위 시작>","timeMax":"<범위 끝>","singleEvents":true,"orderBy":"startTime","q":"<키워드>"}'
   ```

   `singleEvents: true`와 `orderBy: startTime`은 항상 함께 사용하세요 — 이렇게 하면 반복 일정이 하나의 시리즈로 반환되는 대신, 실제로 존재하는 각 회차들이 시간순으로 펼쳐져 나옵니다. 사용자가 어떤 회차를 말하는지 식별할 때 필요한 형태입니다. `q`는 자유 텍스트 필터이며, 사용자가 말한 내용에서 뽑은 `timeMin`/`timeMax` 범위(예: 금요일 얘기를 하다가 바로 "그 회의"라고 하면 범위를 금요일로 좁힘)가 보통 `q` 단독보다 더 안정적으로 범위를 좁혀줍니다.

2. **결과로 판단:** 정확히 하나만 일치 → 진행. 0개 일치 → 못 찾았다고 알리고 더 자세한 정보를 요청하세요. eventId를 지어내지 마세요. 여러 개 일치 → 후보들(제목 + 시간)을 보여주고 어느 것인지 물어보세요. 추측하지 마세요.

3. **바뀐 필드만** `patch`로 적용합니다(전체 리소스를 다시 보내야 하는 `update`가 아닙니다).

   ```bash
   gws calendar events patch --params '{"calendarId":"primary","eventId":"<id>","sendUpdates":"none"}' --json '{"start":{...},"end":{...}}'
   ```

4. 등록 때와 같은 방식으로 **변경 사항을 확인**해주세요.

## 일정 취소 / 삭제

수정 때와 동일하게 먼저 찾지만, 이 스킬이 수행하는 작업 중 가장 신중해야 하는 작업으로 다뤄야 합니다 — CLI 안에서 되돌릴 방법이 없습니다. 일치하는 단 하나의 일정을 찾은 뒤, 그 세부 정보(제목, 날짜/시간, 참석자가 있다면 참석자)를 보여주고 명시적인 진행 승인을 받은 뒤에 실행하세요.

```bash
gws calendar events delete --params '{"calendarId":"primary","eventId":"<id>","sendUpdates":"none"}'
```

추가 확인을 건너뛰어도 되는 유일한 경우는, 사용자가 취소를 요청한 바로 그 메시지에서 일정을 명확하게 특정했을 때(예: 정확한 제목을 그대로 인용했고 일치하는 일정이 하나뿐일 때)입니다 — 그 외에는 항상 삭제하기 전에 무엇을 찾았는지 먼저 보여주세요. 다른 파괴적이고 되돌리기 어려운 작업을 다룰 때와 동일한 원칙입니다.

## 참고 사항

- Calendar의 전문 검색(`q`)은 방금 생성하거나 수정한 일정에 대해 몇 초간 지연될 수 있습니다 — 일정을 등록한 직후 검색으로 다시 찾으려 하면 (insert 호출이 이미 알려준 ID를 쓰는 대신) 결과가 비어 있어도 놀라지 마세요. 방금 다룬 일정이라면 재검색보다 이미 가지고 있는 ID를 우선 사용하세요.
- `gws auth status`에 `calendar` 스코프가 있는 것으로 나오는데도 호출이 인증 오류로 실패한다면, 이 스킬이 필요로 하는 스코프가 알려지기 전에 더 좁은 스코프 집합으로 토큰이 발급됐을 수 있습니다 — 위의 `auth login` 명령을 전체 서비스 목록으로 다시 실행하세요.
- 제공받지 않았거나 찾아서 확인하지 못한 eventId, 참석자 이메일, 시간을 지어내지 마세요 — 대신 물어보세요.
- 사용자가 캘린더를 바꾸는 게 아니라 그저 무엇이 있는지 알고 싶어한다면, 그건 이 스킬이 아니라 `일정관리` 서브에이전트의 역할입니다.
