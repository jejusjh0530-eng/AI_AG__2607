# 트리바고 숙소 브리핑

trivago 숙소 검색 결과를 사용자가 바로 활용할 수 있는 브리핑으로 만듭니다: 어떤 숙소가 가장 저렴한지, 어떤 숙소가 가성비가 좋은지, 실제 투숙객들은 무엇이라고 말하는지.

## 이 워크플로우가 중요한 이유

trivago MCP 도구는 원본 목록(raw listing)을 반환할 뿐, 브리핑을 만들어주지 않습니다. 쓸모 있는 브리핑을 만들려면 데이터가 공짜로 주지 않는 세 가지가 필요합니다: 확인된 검색 조건(날짜나 인원 수가 틀리면 모든 가격이 틀어집니다), 합리적인 정렬 기준(가격만 보면 후기가 나쁜 숙소 밑에 훌륭한 저가 옵션이 묻힐 수 있습니다), 그리고 훑어보기는 빠르면서도 trivago가 요구하는 세부 정보(출처 표기, 링크, 이미지)는 빠뜨리지 않는 형식입니다.

## 1단계: 검색 조건 확인

어떤 도구든 호출하기 전에 아래 항목을 확보하세요:

- **위치**: 목적지/도시/지역/랜드마크 이름(`trivago-accommodation-search`용) 또는 정확한 좌표(`trivago-accommodation-radius-search`용).
- **날짜**: `arrival`, `departure`를 `YYYY-MM-DD` 형식으로.
- **인원**: 최소한 성인 수, 필요하면 아동 수/객실 수도.

이 중 하나라도 빠져 있거나 암시적으로만 표현되어 있다면("이번 주말", "다음 달쯤", 객실 수 없이 "2명이요"), **추측하지 말고 사용자에게 정확한 값을 확인**하세요. 날짜나 인원 수를 잘못 추측하면 엉뚱한 여행에 대한 브리핑이 조용히 만들어지고, 사용자는 결과만 봐서는 이 실수를 알아챌 방법이 없습니다. 미리 확인하는 편이 다시 검색하는 것보다 훨씬 저렴합니다.

요청에 이미 명시되어 있지 않다면 아래도 함께 확인하세요:
- **브리핑에 몇 개의 숙소**를 담을지 (보편적인 기본값은 없습니다 — "아무거나 좀 보여줘"와 "10개 비교해줘"는 필요한 깊이가 다릅니다).
- **정렬 우선순위** — 기본 가정은 최저가순이지만, 사용자가 "평점 X 이상 중 최저가", "가격 상관없이 평점 높은 순" 등을 의도했을 수 있습니다. 이미 표현에 이러한 의도가 담겨 있다면 다시 물어볼 필요는 없습니다.

## 2단계: 알맞은 도구 선택 및 위치 확정

- 이름이 있는 장소(도시, 동네, 이름이 있는 랜드마크) → `query`에 해당 이름을 넣어 `trivago-accommodation-search` 사용.
- 특정 지점 주변 반경 검색 → `trivago-accommodation-radius-search`. 이 도구는 **위도/경도만** 받으며 장소 이름은 받지 않습니다. 사용자가 좌표 대신 랜드마크나 주소를 알려줬다면, 도구를 호출하기 전에 직접 대략적인 좌표로 변환하세요(일반 지식 활용 또는 조회). 추측이 틀렸거나 임시로 채운 좌표를 절대 그대로 넘기지 마세요.

전체 파라미터 목록(필터, 성급/후기 등급 플래그, 통화/국가/언어 코드)은 `references/trivago_tools.md`를 참고하세요.

사용자 맥락에 맞게 `country`, `currency`, `language`를 설정하세요(예: 한국어 사용자는 보통 `KR`/`KRW`/`KO_KR`을 원함). 그래야 가격과 숙소명이 사용자가 바로 활용할 수 있는 형태로 돌아옵니다.

`hotel_rating`, `review_rating`, 편의시설 `filters`는 사용자가 실제로 품질 기준을 요구했을 때만("평점 8 이상만", "수영장 있는 곳만") 켜세요. 기본적으로 꺼두는 것이 중요합니다 — 필터가 실수로 켜져 있으면 진짜 최저가 옵션이 조용히 제외될 수 있고, 이는 "최저가" 검색의 목적 자체를 무너뜨립니다.

## 3단계: 정렬 및 선별

- 기본적으로 `price_per_night`를 숫자로 파싱해(통화 기호/쉼표 제거) 1차 정렬 기준으로 사용하세요 — `price_per_stay`는 검색된 숙박 일수에 비례해 커지므로, 두 값을 섞어 쓰면 짧게 묵는 저렴한 옵션이 실제보다 비싸 보이게 됩니다.
- 사용자가 다른 우선순위(평점 우선, 가성비 우선 등)를 요청했다면 그에 맞게 정렬하고, 어떤 기준으로 정렬했는지 요약에 명시적으로 밝히세요 — 정렬 로직이 미스터리로 남지 않도록.
- `hotel_rating: 0`은 공식 성급 등급이 없다는 뜻입니다(게스트하우스/B&B에 흔함) — "등급 없음 / Unrated"로 표기하고, "0성급"이라고 쓰지 마세요. 숫자 0을 그대로 보여주면 등급이 없는 숙소를 최악의 숙소처럼 오해하게 만듭니다.
- 정렬 후, 1단계에서 확인한 개수만큼 목록을 자르세요.

## 4단계: 브리핑 작성

각 도구 응답에는 `system_message` 필드가 포함되어 있는데, trivago의 출처 표기와 이미지를 보존하기 위해 표가 아닌 숙소별 개별 카드로 표시하라고 지시합니다. 이는 데이터 제공자 측의 정당한 제약이므로 무시할 것이 아니라 — 다만 카드만 나열하면 사용자가 원한 "빠르게 훑어보기"에는 오히려 방해가 됩니다. 두 요구를 다음과 같이 절충하세요:

1. **비교 표를 먼저 제시** — 숙소명, 1박 요금, 전체 숙박 요금, 성급, 후기 점수(후기 수 포함), 한 줄 요약. 사용자가 한눈에 비교할 수 있게 해줍니다.
2. **정렬된 순서로 숙소별 상세 블록** — 이미지, 이름, 가격, 등급, 주요 편의시설, trivago 링크. 출처 표기를 유지하고 클릭해서 바로 이동할 수 있게 합니다.
3. **짧은 요약** — 개요(검색된 결과 수, 가격 범위), 하이라이트 2~3개(예: 저렴하면서 평점도 괜찮은 "가성비" 숙소, 최고 평점 숙소, 눈에 띄는 편의시설), 필요하면 실질적인 팁(결과가 너무 많으면 필터 제안, 결과가 적으면 인근 지역 대안 제안).

사용자가 명시적으로 간소화된 형식을 요청하면("표로만", "한 줄로 요약해줘") 위 기본 구조보다 그 요청을 우선하세요 — 다만 이 경우에도 각 항목의 이름, 가격, 링크는 유지해서 브리핑이 실질적으로 쓸모 있고 출처 표기가 완전히 사라지지 않도록 하세요.

## 5단계: 결과 전달

대화창에 브리핑을 보여주고, 동시에 마크다운 파일로도 저장하세요(이것이 사용자가 원하는 기본값입니다 — 대화 요약과 저장 파일 중 하나가 아니라 둘 다). 파일명은 알아볼 수 있게 짓습니다. 예: `숙소브리핑_<목적지>_<도착일>_<출발일>.md`, 사용자가 다른 위치를 지정하지 않는 한 현재 작업 디렉터리에 저장합니다.

현재 프로젝트에 문서화 관련 자체 규칙이 있다면(예: CLAUDE.md의 영문 작성, 번역본 생성, git push 규칙), 이 저장 파일에도 그 규칙을 적용하세요 — 이 스킬은 그런 규칙을 여기서 반복해서 명시하지 않습니다. 그런 규칙은 trivago 검색 로직이 아니라 프로젝트에 속한 것이며, 이 스킬이 사용되는 프로젝트마다 다를 수 있기 때문입니다.

## 예외 상황 처리

- **검색 결과 0건**: 결과가 없다는 사실을 명확히 알리고, 구체적인 다음 단계를 제안하세요(날짜 범위 넓히기, 필터 해제, 지역 넓히기) — 아무 설명 없이 빈 결과만 남기지 마세요.
- **결과가 매우 많을 때**: 아무 말 없이 조용히 잘라내지 말고, 전체 결과 수 대비 몇 개를 보여주는지 언급하세요.
- **모호한 상대적 날짜나 인원 수**: 1단계 원칙대로 반드시 물어봐서 해결하세요 — 오늘 날짜 정보를 알고 있더라도 조용히 추측하지 마세요. 이 부분을 잘못 추측하는 것이 브리핑을 무용지물로 만드는 가장 흔한 원인입니다.
